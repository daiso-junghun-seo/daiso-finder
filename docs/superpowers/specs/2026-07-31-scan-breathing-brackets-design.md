## 0. 왜 지금

owner 관측: **다른 스캐너 앱은 인식-진행 모션을 보이는데 이 앱은 아무것도 움직이지 않아 "멈춘 것"처럼 읽힌다.** 실제로는 런 F 실측 기준 **초당 50.5회** 디코드를 시도하고 있다(§B30-20 ⑥). 즉 고칠 것은 성능이 아니라 **작동 사실이 화면에 전혀 드러나지 않는 것**이다.

### 이 설계가 서 있는 실측 사실

| 사실 | 출처 | 이 설계에 주는 제약 |
|---|---|---|
| 메인스레드 **96.7% 점유**(시도당 19.17ms × 초당 50.5회) | §B30-20 ⑥ | 모션은 **GPU 컴포지트 전용**이어야 한다 |
| 디코드 루프가 자체 `requestAnimationFrame`을 돈다 | `frameLoop.ts` | JS `rAF` 애니메이션은 **그 루프와 경합**하므로 금지 |
| 매 시도는 프레임 **전체**를 디코드한다 | `frameLoop.ts` (캔버스 1:1 복사) | 공간적 진행을 암시하는 모션은 **거짓말**이 된다 |
| `getUserMedia`가 iOS에서 권한 프롬프트를 포함해 749~1005ms | §B30-20 ⑤ | 마운트 시점 ≠ 디코드 시작 시점 |

### 기록된 전제 하나를 정정한다

§B30-20 ⑭과 `HANDOFF.md`의 "다음 작업 2"는 **브래킷 크롭을 "scan 애니메이션의 메인스레드 예산"으로 정당화**한다. 이 설계는 그 논거가 **성립하지 않음**을 기록한다 — 같은 기록이 애니메이션에 건 하드 제약(GPU 컴포지트 전용)을 지키면 애니메이션은 컴포지터 스레드에서 돌고 메인스레드 예산을 **사실상 쓰지 않는다**(시작 시점의 스타일 계산 1회 제외). 두 항목은 **서로의 전제가 아니다.**

- **애니메이션은 크롭 없이 지금 배송 가능하다** — 이 문서가 그것이다.
- **크롭은 자기 근거(메인스레드를 42%로 되돌린다) 위에 별건으로 남는다.** 크롭은 브래킷 밖 코드를 판독 불가로 만드는 **제품 결정**을 포함하므로(§B30-10, `layout.css`가 현재 *"브래킷은 크롭이 아니다"* 라고 명시) 그 결정과 함께 따로 다룬다.

**owner 결정(2026-07-31): 애니메이션 먼저, 크롭은 별건.**

## 1. 무엇을 만드는가

조준 브래킷(`.scanner-overlay__aim`)이 **카메라가 실제로 프레임을 내보내는 동안에만** 호흡한다. 네 모서리가 함께 약간 커졌다 작아지며 밝기가 오간다.

UI 구조·카피·브래킷 기하는 **불변**이다. 6상태·전이·Zustand 배선·`ScannerPort`·디코드 경로도 **전부 불변**이다.

## 2. 왜 이 모션인가 — 기각된 후보를 함께 남긴다

네 후보를 실제로 움직이는 상태로 비교했다(`.superpowers/brainstorm/`에 목업 보존).

| 후보 | 판정 |
|---|---|
| **A · 스캔 라인**(브래킷 안을 훑는 선) | **기각 — 정직성**. 가장 익숙한 스캐너 관용구지만 "지금 이 띠를 읽는 중"을 암시하는데 **사실이 아니다**. 매 시도는 프레임 전체를 한 번에 디코드하므로 공간적 진행이 존재하지 않는다. 익숙함과 무-날조 규칙이 정면으로 부딪치는 자리이고, 이 저장소에서는 후자가 이긴다 |
| **B · 브래킷 호흡** | **채택**. "살아 있다"만 말하고 어디를·얼마나는 주장하지 않는다. 카메라 영상을 가리지 않는다 |
| **C · 모서리 순환** | 기각. 리듬은 가장 명확하나 순환이 **회전 진행**으로 읽힐 여지가 B보다 크다 |
| **D · 확산 링** | 기각. 중앙→바깥 방향성이 **"더 멀리 대라"** 로 읽힐 수 있는데, 런 F가 보여준 필요는 반대였다(심볼이 브래킷 한 변의 11.3%, §B30-20 ⑧) |

## 3. 시작 시점 — `playing`, 마운트가 아니다

오버레이는 마운트 즉시 브래킷을 그리지만 그 시점에 디코드는 돌지 않는다. `scan()`은 ① 디코더 결정(네이티브 질의 또는 ~76 kB zxing import) → ② `getUserMedia`(iOS에서 **권한 프롬프트 = 사람 시간**) → ③ zoom 적용 → ④ 프레임 루프 순서다.

**`<video>`의 `playing` 이벤트를 기다린다.** 영상이 흐른다 = 카메라가 프레임을 내보낸다 = 루프가 그 프레임을 소비한다. 오버레이가 이미 소유한 DOM 이벤트라 **`ScannerPort` 변경이 없다**.

기각한 대안: 포트에 진행 신호 추가 — 가장 정확하지만 도메인 포트 계약을 바꾸고 mock 스캐너·E2E·합성 루트까지 번진다. 지금 얻는 것에 비해 비싸다.

**해제 코드는 없다.** 안내(notice)가 뜨면 브래킷 자체가 언마운트되고(기존 배선 — *"카메라가 실패했는데 조준을 지시하는 것은 앱이 지킬 수 없는 약속"*), 성공·취소는 오버레이가 통째로 사라진다. 성공 직후 언마운트까지의 약 1프레임 동안 카메라가 멈춘 채 모션이 남을 수 있으나, 그 창은 관측 불가능하고 정직성을 해치지 않는다.

## 4. 구현

### 4.1 `ScannerOverlay.tsx`

```tsx
const [streaming, setStreaming] = useState(false);

<video … onPlaying={() => setStreaming(true)} />

<div
  className={`scanner-overlay__aim${streaming ? ' scanner-overlay__aim--live' : ''}`}
  aria-hidden="true"
>
```

`aria-hidden`은 그대로다 — 모션은 장식이며 모든 상태는 아래 텍스트가 말한다.

### 4.2 `layout.css`

```css
.scanner-overlay__aim {
  /* …기존 선언 유지… */
  --aim-breathe-duration: 1.3s;
  --aim-breathe-scale: 1.09;
  --aim-breathe-dim: 0.32;
}

.scanner-overlay__aim--live {
  animation: aim-breathe var(--aim-breathe-duration) ease-in-out infinite;
  will-change: transform, opacity;
}

@keyframes aim-breathe {
  0%, 100% { transform: translate(-50%, -50%) scale(1);                        opacity: var(--aim-breathe-dim); }
  50%      { transform: translate(-50%, -50%) scale(var(--aim-breathe-scale)); opacity: 1; }
}
```

**지역 `@media (prefers-reduced-motion: reduce)` 블록은 쓰지 않는다 — 2026-07-31 플랜 작성 중 정정.** `tokens.css:46`에 이미 전역 규칙이 있다:

```css
@media (prefers-reduced-motion: reduce) {
  * { animation: none !important; transition: none !important; }
}
```

`!important`가 `--live`의 `animation`을 이긴다. 그리고 `.scanner-overlay__aim` 기본 규칙에는 `opacity` 선언이 **없으므로** 애니메이션이 죽으면 초기값 `1`로 돌아간다 — 설계가 요구한 **"완전 불투명한 정적 브래킷"이 추가 코드 없이 나온다.** 지역 블록을 또 쓰면 중복일 뿐 아니라 전역 규칙을 신뢰하지 않는다는 잘못된 신호가 된다.

**대신 그 전역 규칙이 이 기능의 하중 부재가 되므로 테스트를 붙인다**(§7 ⑤) — 현재 `src/styles/tokens.test.ts`에 `reduced-motion` 언급이 **0건**이라, 그 블록을 지워도 전 스위트가 통과하고 모션 감소를 설정한 쇼퍼가 호흡을 그대로 보게 된다. 이 설계 이전에는 무해한 누락이었고, 이 설계가 그것을 결함으로 만든다.

세 가지를 명시한다:

1. **`translate(-50%, -50%)`는 키프레임마다 다시 써야 한다.** `transform`은 단일 속성이므로 키프레임이 기본 규칙의 중앙 정렬을 **덮어쓴다** — 빠뜨리면 브래킷이 화면 중앙에서 벗어난다.
2. **`will-change`는 의도적 결정이다.** 96.7% 포화 상태에서 컴포지터 레이어 승격을 보장하려는 것이고, `<video>` 위에 레이어를 하나 더 올린다. 되돌리기 쉬우며, 실기기에서 리페인트 이상이 관측되면 제거 대상 1순위다.
3. **CSS 변수는 값을 한 곳에 모을 뿐 런타임 조정 능력을 주지 않는다.** `?debug=1&breathe=…` 같은 오버라이드는 **만들지 않는다**. 실기기에서 세기를 바꾸려면 이 값을 편집하고 다시 빌드한다.

### 4.3 값의 출처와 한계

`1.3s / +9% / 밝기 32→100%`는 세 단계를 나란히 움직여 놓고 고른 **출발점**이다. **정직하게 기록한다 — 이 선택은 정지된 모의 배경을 모니터로 보며 한 것이고**, 실제로는 손떨림이 있는 움직이는 카메라 영상 위에 얹힌다. 그 위에서는 같은 값이 더 약하게 느껴지는 것이 보통이므로, 실기기 확인 후 조정될 수 있다.

## 5. 정직성 — 이 모션이 주장하는 명제

**"카메라가 프레임을 내보내고 있다"** 하나뿐이고, `playing` 이벤트가 정확히 그 뜻이다.

- 진행률을 주장하지 않는다 — 진행이 존재하지 않는다. 각 시도는 독립이고 런은 1.0초에서 7.4초까지 흩어진다(런 D~F).
- 위치를 주장하지 않는다 — 프레임 전체를 디코드하므로 "여기를 읽는 중"이라 할 지점이 없다.
- 성공 모션은 만들지 않는다 — 성공하면 오버레이가 즉시 닫히므로 볼 시간이 없다. 만들면 보이지도 않는 것에 코드를 쓰는 셈이다.
- 실패하면 사라진다 — 기존 배선이 이미 그렇게 한다.

## 6. 접근성

`prefers-reduced-motion: reduce`에서 모션을 끄고 **완전 불투명한 정적 브래킷**으로 둔다. 이는 `tokens.css:46`의 **전역** 규칙이 이미 제공하며 이 기능은 코드를 더하지 않는다(§4.2) — 대신 그 규칙에 **처음으로 테스트를 붙인다**(§7 ⑤).

조준 안내(`SCAN_AIM_GUIDE`)와 `aria-describedby` 배선은 불변이므로, 모션이 없어도 쇼퍼가 잃는 정보는 없다 — 모션은 텍스트가 이미 말하는 것에 아무것도 더하지 않는 장식이다.

---

## 7. 테스트

CSS는 렌더 결과를 단위 테스트로 볼 수 없다(Vitest가 평문 CSS import를 스텁하고 jsdom이 이 파일을 적용하지 않는다 — `layout.test.ts` 주석). 그래서 **상태 전이는 컴포넌트 테스트로, 스타일시트 내용은 텍스트 가드로** 나눠 고정한다.

**신규는 5건이다.** "안내가 뜨면 브래킷이 사라진다"는 **이미 고정되어 있다** — `ScannerOverlay.test.tsx`의 `the corner brackets disappear once an outcome notice replaces the guidance`(권한거부 경로). 브래킷이 사라지면 모션도 함께 사라지므로 이 설계가 그 명제에 추가로 요구하는 것은 없다. **플랜은 이것을 신규 테스트로 다시 쓰지 않는다** — 이미 있는 것을 신규로 세면 커버리지를 과대 보고하게 된다.

`ScannerOverlay.test.tsx` (신규 2):

1. 마운트 직후 브래킷에 `--live`가 **없다** — 권한 프롬프트가 떠 있는 동안 "읽는 중"이라 말하지 않는다는 명제 그 자체
2. `<video>`에 `playing`을 발생시키면 `--live`가 **생긴다**

`layout.test.ts` (기존 `ruleFor` 패턴, 신규 3):

3. `.scanner-overlay__aim--live`가 `animation`을 **선언한다** — **긍정 단언**. 이 저장소는 금지 단언만 둔 CSS 가드가 "선언을 지워도 전부 통과"하는 것을 이미 한 번 겪었다(§B30-15 ④)
4. `@keyframes aim-breathe`가 `transform`·`opacity` **외의 속성을 건드리지 않는다** — 레이아웃 속성이 들어오면 GPU 전용 제약이 조용히 깨지고 96.7% 포화 위에서 디코드 루프와 경합한다
`tokens.test.ts` (신규 1):

5. `tokens.css`의 전역 `prefers-reduced-motion: reduce` 블록이 `animation`을 끈다 — **이 설계가 접근성을 그 규칙에 의존하게 만들므로**(§4.2·§6) 이제 하중 부재다. 현재 이 파일에 `reduced-motion` 단언은 **0건**이라, 블록을 통째로 지워도 전 스위트가 통과한다

**키프레임과 미디어 블록은 `ruleFor`로 읽을 수 없다** — 기존 헬퍼는 `css.indexOf('}')`로 잘라내므로 중첩 중괄호를 가진 `@keyframes`·`@media`에서는 **첫 내부 블록만** 반환한다. 중괄호 짝을 세는 `blockFor(header)` 헬퍼를 새로 만든다(플랜 Task 2·3에 코드 포함).

**이빨은 뮤테이션으로 실증한다**: `animation` 선언 삭제 → 3번 사망 / 키프레임에 `height` 주입 → 4번 사망 / `tokens.css`의 전역 reduced-motion 블록 삭제 → 5번 사망 / `onPlaying` 제거 → 2번 사망 / `--live`를 무조건 붙이기 → 1번 사망. 살아남는 뮤테이션이 있으면 그 자체가 findings다.

E2E는 추가하지 않는다. dev/E2E는 무-카메라 mock 스캐너로 도는 경로라 `<video>`가 실제로 재생되지 않으므로, E2E가 고정할 수 있는 것은 단위 테스트가 이미 고정한 것보다 적다.

## 8. 하지 않는 것

- **브래킷 크롭** — 별건(§0). 제품 결정을 포함하고 이 모션의 전제가 아니다.
- **JS `requestAnimationFrame` 애니메이션** — 디코드 루프 자신의 rAF와 경합한다.
- **`ScannerPort` 변경** — `playing`으로 충분하다.
- **런타임 튜닝 오버라이드** — §4.2 ③.
- **성공 모션** — §5.

## 9. 게이트

기존 게이트 전항목(vitest · tsc · biome · Playwright · build)이 GREEN이어야 하고, 신규 단위 테스트 **5건**(vitest 537 → **542** 예상)이 각자의 뮤테이션으로 이빨을 증명해야 한다. 엔트리 청크는 **CSS만 늘고 JS는 사실상 불변**일 것으로 예상하며, 실측치를 커밋 본문에 기록한다.
