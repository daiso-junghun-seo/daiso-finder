### P3 Flow 3 Alternative Discovery — 구현 완료 (2026-11-12)

- **발행 범위**: Group A(similar, 이 매장)만 live. Group B(nearby)는 포트·타입·mock·표면·E2E·axe까지 구현하되 프로덕션 어댑터는 등록하지 않는다(`NEARBY_LIVE=false`) — `hldyDt` 단일 샘플·A7(판매종료 scope)·nearby 임계값 미정(D3). withheld 슬롯은 아무 것도 렌더하지 않는다.
- **진입·소유권**: Flow 1 일시품절·판매종료 + Flow 2 soldOut/recoveryStill. 목록→store card→Flow 2 overlay 스택은 `AlternativeSurface`가 소유하고, 부모는 진입 상태·`backSignal`·`onDepthChange`만 갖는다. Flow 1이 연 Flow 2는 `hidden`으로 남겨 soldOut exit phase를 보존하고 hidden 동안 resume refresh를 하지 않는다. back은 3단(목록→Flow 2→Flow 1)으로 포커스를 되돌린다.
- **데이터**: `POST /api/alternatives` = SearchGoods 30(store-carryable) → `selStrPkupStck` 배치 1회(qty>0, vendor 순서) → 앞 3개 위치 병렬. 위치 없는 행 omit(no backfill), `omitted>0 && rows=[]` → failed.
- **캐시·신선도**: 통짜 캐시(키 `${strCd}:${pdNo ?? keyword}`, `issued` 포함), 성공 답만 저장, **전부 실패**일 때만 Partial 서빙. 스탬프는 가장 오래된 관측 1회, 모든 발행 슬롯 settle 전 미표시. TTL 없음, 공유 6h 임계값.
- **상태·렌더**: 행 0 + failed = Error, empty+withheld = degraded Empty(mall 제외), 전부 empty만 정상 Empty(양쪽 발행 시 mall 허용). 혼합 답의 failed 슬롯은 그룹 자리에서 실패 문장 + slot retry만 렌더하고 empty 문장을 빌리지 않는다(spec §5.1 2026-11-12 수정). 재입고 알림은 P3 미렌더.

### P2 Flow 2 In-Store Navigation (2026-11-10)

- **데이터 인-핸드 진입**: Flow 1 Success의 답(상품·가격·층/구역·스탬프)을 그대로 넘겨받아 요청 없이 즉시 안내를 렌더한다. handoff는 `navigationEntryOf`(candidate/scan → pdNo, typed → 키워드, 미보유 시 표시 쿼리 → 상품명 폴백) — 새 캐시 단위를 만들지 않는다.
- **배경 새로고침**: `navigation-refresh.ts` 2s 타임아웃·비블로킹·주기 타이머 없음. 트리거 = 진입·resume·pull·`못 찾겠어요` 1회·stale `다시 확인`. outcome 4종(`unchanged`·`changed`·`soldOut`·`unapplied`) 중 `temporarilyOut`만 sold-out exit.
- **D4 보류**: mid-walk 위치 이동·판매종료·franchise flip은 Bible Experience 결정이 없어 `unapplied`로 안내를 유지한다(앱이 종료 카피를 발명하지 않는다).
- **표면**: `NavigationSurface` 6상태 — 다중 위치 선택 → 단일 안내(L3 다른 위치 disclosure) → `못 찾겠어요` recovery(다른 위치 / 직원 문의 + `대안 보기`) → 품절 → stale(시스템 오류 본문 + `다시 확인`). Flow 2에서는 검색바·카트 링크를 숨기고, back은 `위치 보기` CTA로 포커스를 되돌린다.
- **검증**: 단위 60건 신규(navigation-refresh 16·entry 8·dev-refresh 5·표면 16·handoff 5 등), E2E `navigation.spec.ts` 12건, axe Flow 2 4상태×2테마 8건. dev 하네스 `?navRefresh=`·`?navAge=`는 `import.meta.env.DEV` 게이트이며 entry 호출은 unchanged로 유지한다(쇼퍼가 먼저 안내를 본다). 결정 = [`notes/open-questions.md`](notes/open-questions.md) §B49.
- **짧은 폰 예산**: Flow 2 CTA가 320×568에서 예산을 넘겨 사진 하한을 112→80px로 내렸다. L4 액션 줄이 wrap된 경우(CI Linux 폰트에서 먼저 드러남)를 긴 매장명으로 재현해 E2E 기하 케이스로 고정했다(§B49-8).

- **레이아웃 하드닝**(§B48): 렌더 페이지를 390×844·375×667·320×568·1280×800에서 실측한 뒤 수정. 375×667에서 가격·`담기`가 도킹 바에 가려지고 320×568에서는 가격이 전부 가려지던 문제, 스크롤 시 답 카드가 매장 바를 덮던 스태킹, 데스크톱 시트가 1280px 전체를 차지하고 카트 시트 패딩이 0이던 문제, UA 기본값(content-box·블록 마진·음절 중간 줄바꿈)을 제거. CSS 텍스트 가드 + 렌더 기하 E2E 7건으로 잠갔다.

- **IndexedDB 연결 재사용**, **adapter→ui import 금지 가드**, `kmToMeters`(테스트 전용) 제거.

다음 우선순위는 이 계측기로 하는 **실기기 측정**이다. **비교 기준에 주의**: 조준 가이드(§B30-13) 질문은 `de5b49a`와 동등한 코드(그 위는 문서만 갱신된 커밋들)를 기준선으로 삼을 수 있었지만, **프레임 루프 질문에는 비교 가능한 기준선이 아예 없다** — `decodeAttempts`·`decodeMs`가 "라이브러리 내부 재시도"에서 "앱 소유 루프"로 **의미 자체가 바뀌었기 때문**(§B30-14 ⑥). 그래서 이번 1단계 측정은 옛 수치를 이기는 비교가 아니라 **새 기준선을 세우는 측정**이다.

절차: PowerShell은 `$env:HOST='0.0.0.0'; $env:DIAG_TIMING='1'; npm run dev:live`(문서의 `HOST=0.0.0.0 …` 한 줄 표기는 bash 전용이라 PowerShell에서 동작하지 않는다). `DIAG_TIMING='1'`은 2026-09-03 프록시 상류 계측(§B30-24)을 켠다 — **기본은 OFF**이고, 이 값을 빼면 응답에 `server-timing`이 실리지 않고 패널도 이 브랜치 이전과 동일하게 렌더한다. **읽는 규칙**: 완료된 조회 한 건에 `상류`가 한 줄도 안 보이면 `DIAG_TIMING`이 꺼진 것이다(성공한 조회는 3중 조회 중 승자가 반드시 하나 있으므로 이 규칙이 성립한다 — 줌 오버라이드에서 `줌 요청:` 줄을 읽는 규칙과 같은 이유). **폰은 HTTPS가 필수**다 — LAN IP를 http로 열면 `secureContext:false`가 되어 카메라 자체가 열리지 않으므로, 터널(localtunnel 등)은 대안이 아니라 요건이다. 동일 기기·동일 상품·권한 이미 허용 상태로 **최소 2회 측정**하고, 권한 프롬프트가 낀 첫 런과 스캔 도중 백그라운드로 전환된 런은 비교에서 제외한다. **zoom 스윕 전용 URL 두 개(2026-08-03, §B30-23)** — 같은 고정 거리에서 `?debug=1&zoom=1`과 `?debug=1&zoom=2`를 각각 열어 `심볼 크기`를 비교한다. `zoom`은 `debug`와 달리 지속되지 않으므로(매 로드 재해석) 런마다 URL을 다시 쳐야 하고, 오타·범위 초과 값은 조용히 무시되지 않고 오버라이드가 **거부**되어 그 런은 2.0으로 돈다 — 그래서 아래 `줌 요청` 줄이 반드시 함께 기록해야 하는 항목이다. 매 런마다 `스캔 소요` · `카메라 승인` · **`줌 요청`** · **`줌 적용`** · **`줌 소요`** · **`심볼 크기`** · `디코더 준비` · `시도 횟수` · `디코드 점유(조립 포함)` · `비트맵 조립` · `프레임 복사` · `루프 대기` · `워밍업 대기` **13개 값**을 함께 기록한다(`워밍업 대기`·`비트맵 조립`은 2026-07-30 최종 리뷰 수정 웨이브 신설 — §B30-15; `줌 적용`·`줌 소요`·`심볼 크기`는 2026-07-30 zoom 웨이브 신설 — §B30-17; **`줌 요청`은 2026-08-03 zoom 오버라이드 신설 — §B30-23**, 오버라이드가 파싱되지 않은 런에서는 이 줄 자체가 패널에 없다는 것도 함께 적을 것). **읽는 규칙 — `줌 요청`이 있어도 `줌 적용: 미보고`만으로 "플랫폼이 답하지 않았다"고 단정하지 말 것**: 오버라이드가 파싱됐다는 것과 카메라가 zoom capability를 보고한다는 것은 별개다. 카메라가 zoom capability를 아예 보고하지 않으면 `줌 요청`이 있어도 시도 자체가 없어 아래 판정 표의 "`줌 적용`이 미보고인데 `줌 소요`는 숫자다" 행이 아니라 "`줌 적용`·`줌 소요` 둘 다 미보고" 행이 뜬다 — 겉보기엔 같은 두 줄(`줌 요청` 존재 + `줌 적용: 미보고`)이 두 가지 서로 다른 사실을 가리킬 수 있다는 뜻이다. 둘을 가르는 것은 `줌 소요`다: 숫자면 요청이 실제로 카메라까지 갔다는 뜻이고, `미보고`도 같이 뜨면 시도 자체가 없었다는 뜻이다. **패널이 새로 출력하는 캡처빌리티 두 줄**(`지원 제약:` · `카메라 기능:` — `report.ts`의 `captureCapabilitiesLine`, §B30-16)도 함께 받아 적는다: 다음 레버가 `zoom`인지 확인하는 데 쓰인다(2026-07-30에 이미 그 아이폰에서 `zoom=0.5~10`·`torch=true`, `focusMode`는 `지원 제약`에 없음 — 설정 불가로 확인됨, §B30-16 ④; 런 F는 `focusDistance=0.02~미보고`가 `카메라 기능`에만 나타나고 `지원 제약`에는 없음을 재확인했다 = **읽기는 되고 설정은 안 되는 capability**).

**⚠️ `카메라 기능:` 줄의 범위 표기가 `86ac4e5` 이후 달라졌다 — 눈대중 비교 시 불일치로 오독하지 말 것.** 범위는 이제 `<키>=<min>~<max>[ step=<step>]`로 렌더되고, `step`은 **플랫폼이 보고했을 때만** 붙는다(`report.ts`의 `rangeText`). 읽는 규칙: **`step`이 안 보이면 플랫폼이 말하지 않은 것**이지 "우리가 재지 못한 것"이 아니다(그래서 `step=미보고` 같은 잡음을 만들지 않는다). 반대로 **측정된 `step=0`은 값이므로 0으로 찍힌다**(측정된 0ms·0px과 같은 규율 — 검사가 truthiness가 아니라 `== null`이다). 따라서 위에 인용된 `zoom=0.5~10`이 zoom 스윕에서 `zoom=0.5~10 step=0.1`로 보여도 **정상**이고, 그 `step`은 "1.5를 요청할 수 있는가"에 직접 답한다.

| **아주 가까이** 든 스캔이 이전보다 **나빠졌다** | §B30-17 ⑩의 기록된 리스크(2×에서 심볼이 프레임을 넘쳐 quiet zone 상실)가 현실화한 것 — **상한을 낮추는 것이 대응**이다. 일어난다고 미리 단언하지 않았으므로 관측되면 그대로 기록한다 |

**`심볼 크기` → 모듈당 픽셀(PPM) 환산은 여기서만 한다 — 패널에는 없다.** 패널이 픽셀만 내는 이유는 `Result`가 모듈 수를 갖고 있지 않아서이고(§B30-17 ⑥), 따라서 환산은 **가정을 명시한 파생값**이다:

- **PPM ≈ `심볼 크기` ÷ 모듈 수**, 그리고 **가정 = owner 표본의 심볼이 16×16으로 보였다**(표본 1개, 미확정). DataMatrix는 10×10·12×12·14×14·16×16·… 이 있으므로 **모듈 수가 다르면 이 숫자는 그만큼 틀린다** — 그래서 코드가 아니라 여기 있다.
- 예: `심볼 크기: 168px`이고 16×16이면 PPM ≈ 10.5. zxing-cpp가 서브픽셀 디텍터를 추가한 구간인 **"약 2 px/module"** 과 이 값을 비교하면, 옛 디텍터의 고해상도 전제(§B30-17 ⑦)에 이 프레임이 부합하는지 가늠할 수 있다.
- **실측 환산(런 F, 2026-07-30)**: `심볼 크기: 73px` → **PPM ≈ 4.56**, 반-모듈 편향 보정 시 ≈**4.7**(16×16 **가정** 아래). 위 예(168px → 10.5)보다 **2.3배 나쁘다**. zxing-cpp가 서브픽셀 디텍터를 추가한 **"약 2 px/module"** 보다는 아직 위지만, 옛 디텍터가 전제하는 고해상도 영역과는 거리가 멀다(§B30-17 ⑦).
- **브래킷 대비 비교(런 F, 파생값 — 계산 근거를 여기 남긴다)**: 조준 사각형은 프리뷰 **짧은 변의 60%**(`src/styles/layout.css`의 `height: 60%` + `aspect-ratio: 1`)이므로 1920×1080에서 `0.6 × 1080` = **648 비디오 px**이고, `symbolSidePx`는 **같은 캔버스 좌표계**의 값이다(`frameLoop.ts`가 `videoWidth/videoHeight`로 캔버스를 잡고 1:1로 복사하므로 숨은 배율이 없다). 따라서 심볼은 브래킷 한 변의 **73/648 = 11.3%**, 면적으로는 ≈**1.3%**였고 브래킷을 채우려면 선형으로 ≈**8.9배**가 더 필요하다. **크롭 투영(관측이 아니라 투영)**: 브래킷만 그리면 픽셀이 `648²/(1920×1080)` = **20.25%**이고, `비트맵 조립`·`프레임 복사`는 픽셀 비례(`getImageData` 리드백 + greyscale + binarize / GPU측 `drawImage`)이므로 각각 ≈**2.4ms**·≈**0.4ms**로 떨어져 시도당 실작업 ≈**8.3ms**, 같은 시도율에서 메인스레드 점유 ≈**42%**가 된다 — **측정된 비례성에서 파생한 값이며 관측된 값이 아니다.**
- **작은 계통 편향 1건(정직하게 명시)**: 디텍터는 코너를 반환 전에 **모듈 중심으로 이동**시킨다(`shiftToModuleCenter`, 설치본 `Detector.js` — *"shift points to the center of each modules"*). 그래서 이 길이는 인쇄된 심볼의 **바깥 변보다 약 반 모듈 짧다**(16모듈이면 수 %). **비례 관계는 이 편향에 무관하다**(편향이 모듈 크기에 비례하므로 두 zoom 수준의 **비**에서 상쇄된다) — 위 표의 첫 행 판정에는 영향이 없고, PPM **절대값**에만 몇 % 보수적으로 작용한다.

**세 번째 최상위 질문(2026-07-30 신설, §B30-18) — `/api/availability` 병렬 3중 조회가 배송됐다.** 위 두 질문(페이싱·zoom)은 **디코드**를 다루고 이 질문은 **조회**를 다루므로 서로 독립이며, 같은 런의 `[네트워크]` 블록으로 함께 답한다.

**먼저 알아야 할 것 — 이 질문의 배경은 우리 코드의 타임아웃이다.** 관측된 `error · 2002ms` 2건은 벤더가 아니라 `src/infra/query-cache.ts:21`의 **`?? 2000`** 이다(§B30-18 ①). 실측 성공 최대는 **1445ms**, 산포는 442~1445ms(3.3배)라 벤더 지연이 이 상한과 동전 던지기 거리에 있다. **2000ms는 지금은 올리지 않았다**(**⚠️ 2026-07-30 정정 — 이유가 "Bible 소유"에서 "현장 근거 부족"으로 바뀌었다**: Engineering `:58`이 *2s 수치 자체*를 `Hypothesis — requires field validation` 으로 명시하므로 앱이 현장 근거로 정제할 수 있는 값이다. 막고 있는 것은 권위가 아니라 근거다 — 실측이 전부 터널을 통과했고 프록시가 업스트림 소요를 보고하지 않아 경로/벤더 지연이 분리되지 않는다. 다음 걸음은 owner escalation이 아니라 **프록시 업스트림 계측**이다. §B30-18 ②) — 병렬 3중은 상한을 올리는 대신 **3표본의 최솟값**으로 상한 아래 착지 확률을 높이는 헤지다(§B30-18 ④). 요청별 마감은 **1800ms**(러너 상한 200ms 아래 — 그래서 타임아웃이 러너의 눈먼 abort에 가려지지 않고 `시간 초과`로 보고된다).

패널 `[네트워크]`는 이제 조회 1회당 **3줄**이고 각 줄에 `#i/3` 라벨이 붙는다. **한 조회의 3줄만 묶어서 읽을 것** — 목록은 세션 누적이라 12줄이면 최대 4개 조회가 섞여 있다(`NETWORK_LIMIT = 12`).

**⚠️ dev 터널 런만으로는 벤더 신뢰성을 판정할 수 없다.** 이전 세션의 `408` 3건은 **localtunnel이 원인이었고 벤더가 아니었음이 확증됐다** — 다른 터널로 바꾸자 200이 돌아오고 앱이 `state: success`에 도달했다. 따라서 이번 런에서 `error 질의 실패`나 `시간 초과`가 나오면 **먼저 터널을 의심**하고, 최소한 (a) 터널을 바꿔 재현되는지, (b) 같은 시각 `/api/search`·`/api/stores` 줄도 같이 나빠지는지(그러면 경로 공통 = 터널)를 확인해야 한다. **벤더 신뢰성의 최종 판정은 gpu01 직접 서빙(게이트 1번) 뒤**로 미룬다.

| `루프 대기` | 우리가 페이싱으로 버린 시간 | **상수가 0으로 배송된 뒤로는 이 값이 곧 rAF 대기다** — `FRAME_LOOP_MIN_INTERVAL_MS`가 0이라 더 이상 우리가 고른 간격을 곱해 비교할 대상이 없다. 그런데도 이 값이 크면 rAF 자체가 늦게 오는 것(메인 스레드 부하)이며 **워밍업이 아니다** — 워밍업은 자기 필드가 있다 |
| `워밍업 대기` | 비디오가 첫 프레임(치수)을 낼 때까지 우리가 기다린 시간 | 크면 원인은 디코더도, 간격도, 해상도도 아니다 → 루프 시작을 `loadedmetadata`에 걸거나 카메라 기동 비용으로 수용 |
| 잔차 = `스캔 소요` − `카메라 승인` − **`줌 소요`** − `디코더 준비` − (`디코드 점유` + `프레임 복사` + `루프 대기` + `워밍업 대기`) | 계상 못 한 시간 | **`비트맵 조립`은 더하지 않는다** — `디코드 점유`의 부분집합이라 더하면 이중 계상되어 잔차가 음수로 간다. **`줌 소요`를 빼는 것은 2026-07-30 정정이다**(정정 전 식에는 이 항이 없었다): `줌 소요`는 패널이 찍는 **이름 있는 구간**이면서 `스캔 소요` **안**에 있고 `카메라 승인` **밖**에 있으므로(§B30-17⑤), 빼지 않으면 배송된 zoom 재구성 비용이 잔차에 들어앉아 "이름 없는 구간"으로 오독된다. **런 F가 규칙을 쓴 직후 첫 런에서 그것을 실증했다** — `줌 소요`를 빼면 잔차 **정확히 0ms**, 빼지 않으면 **308ms**. `줌 소요`가 `미보고`면(zoom을 아예 시도하지 않은 런) 그 항은 **0**이다. 워밍업도 더 이상 잔차의 후보가 아니다(자기 필드로 분리됨). 이 둘을 뺀 뒤에도 잔차가 크다면 그때 비로소 **아직 이름 없는 새 구간**이라는 뜻이다. **이 표는 "실측 전 예측으로 보존"의 대상이 아니다** — 그 라벨은 위 세 개의 최상위-질문 표에만 걸리고, 이 표는 스스로 **운영 규칙**을 선언하므로 틀린 규칙은 보존하지 않고 정정한다 |

**이전 절차의 "2번째 arm"(간격 상수를 로컬에서만 0으로 낮춰 대조 측정하는 단계)은 제거한다** — 그 arm이 재던 것이 이제 **배송된 기본값 자체**이기 때문이다(§B30-16). 대조 없이 직접 관측하면 되므로 별도 arm은 더 이상 필요 없다.

**성공의 기준은 "빨라졌다"가 아니라 구간들이 분리되어 병목이 표본-제한인지 시간-제한인지 귀속 가능해지는 것**이다 — 느려졌다면 그것대로 기록한다(§B30-16 ③의 메인스레드 리스크가 현실화했을 수 있다는 뜻이다). 이 실기기 측정은 owner가 직접 확인해야 하는 항목이라 새 세션이 대신할 수 없다. 측정 후 **2단계 후보 서열**과 `main` 로컬 머지 여부를 함께 결정한다. **후보들은 서로 다른 구간을 겨누므로 대안이 아니다** — 어느 값이 컸는지에 따라 서열이 갈린다(2026-07-30 정정, §B30-17 ⑨):

1. **카메라 `zoom`** — **이미 배송됐다**(상한 2.0, §B30-17). 남은 것은 측정이고, 결과에 따라 상한 재검토나 업스케일이 이어진다. `focusMode`는 이미 폐기됨(§B30-16 ④), `tryHarder`는 이 라이브러리의 DataMatrix에 **효과가 없음이 확인됨**(§B30-17 ⑧).
2. **브래킷 크롭** — **디코드 레버는 여전히 아니지만, 정당화가 바뀌었다(2026-07-30, 런 F).** 줄어드는 것은 `비트맵 조립`·`프레임 복사`이고 **모듈당 픽셀은 올라가지 않는다** — 같은 심볼이 같은 픽셀 수를 차지하므로 **크롭 단독으로는 판독 거리가 늘지 않고**, 거리에 영향을 주려면 **업스케일 또는 zoom과 짝지어야** 한다(§B30-17 ⑨). 바뀐 것은 **왜 필요한가**다: 런 F가 메인스레드 **96.7% 점유**를 실측했고(시도당 19.17ms × 초당 50.5회), owner가 요청한 **scan 애니메이션의 하드 제약**(GPU-컴포지트 전용, JS rAF 루프 금지 — §B30-19⑤)이 **바로 그 포화 때문에** 존재한다. 브래킷 크롭은 픽셀을 20.25%로 줄여 점유를 ≈**42%**로 되돌린다(투영). 즉 크롭은 이제 **디코드 수정이 아니라 애니메이션의 메인스레드 예산**으로 정당화된다 — **결정이 아니라 근거가 바뀐 후보**다. 런 F 형상(심볼 = 브래킷 한 변의 11.3%)에서는 심볼을 자르지 않는다. 제품 결정도 포함한다(상자 밖 코드가 안 읽히게 된다 — §B30-10). *정정 전 이 줄은 크롭을 zoom과 같은 문제에 대한 대안처럼 나열했다.*
3. **`zxing-wasm` 이관** — **근거가 속도에서 판독성으로 바뀌었다.** 속도 근거는 여전히 기각인데, **기각의 근거는 퍼센트가 아니다**: 앱은 이미 초당 **~48-50회** 시도하는 반면 카메라는 **30fps**이므로, 더 빠른 디코더는 **시도 수만 늘리고 새 프레임은 만들어 주지 못한다**(§B30-17 ①). *(퍼센트를 근거로 쓰지 않는 이유 — 정정 2026-07-30: 이전 서술 "디코더 5.4ms/시도 = 4.4%"는 **두 런을 섞은 식**이었다. `4.4%`는 **200ms 페이싱 런**의 값이고 그 런의 디코더는 시도당 **9.4~11.5ms**였다(§B30-16 ①); `5.4ms/시도`는 **페이싱 0 런**의 값이며 거기서 디코더 자신의 비중은 **16~26%**다(런 F: **23.6%**). 둘을 곱해 하나의 등식으로 읽으면 안 된다.)* 이 후보를 다시 연 것은 `@zxing/library`가 zxing의 **옛 고해상도 DataMatrix 디텍터만** 싣고 있고 저해상도용 **서브픽셀 디텍터가 이 패키지에 없다**는 사실이다(§B30-17 ⑦) — 런 F의 PPM ≈ 4.6이 그 판단의 실측 입력이다.

**이 서열의 1번(zoom)은 이미 배송됐고 지연시간은 런 D·E·F로 측정됐으나, 모듈당 픽셀 효과는 여전히 미검증이다(§B30-19④ — 런 F도 `줌 적용: 2`라 `zoom ≠ 2` 표본이 없다)** — 이 문서 맨 위 "다음 세션 순서"가 지정한 **zoom 스윕**이 이 서열의 다음 걸음이고, **그 앞에 수정 웨이브의 독립 리뷰 → `main` 머지 → 크롭 + scan 애니메이션**이 온다(owner 요청 + 애니메이션의 메인스레드 예산이 크롭을 같은 걸음으로 묶는다). 그 다음(zoom 스윕·2단계 서열이 정리된 뒤) = 🟢 슬라이스 3번(UI 폴리싱 — 후보 리스트 + 사진 스타일) (1번 후보품질 튜닝 ✅ 2026-07-24 `8518337`; 2번 바코드 스캔 ✅ 2026-07-25/26 **`main` 병합 완료**(`9570096`, DataMatrix 정정 `6c33189`)). 스코프 주의 = `.candidate-list`·`.product-photo`(+ 스캔 오버레이 `.scanner-*`)의 **바운드 프레젠테이션 패스, 카피·마크업 시맨틱 불변**. 큰 수(배포·AI 티어링·반대형)는 owner court(ToS·Bible)라 게이트가 풀린 뒤. 병렬 서브에이전트로 최적화하며 진행 가능. 로컬 테스트는 언제든 `npm run dev:live`.

**불변 원칙**: UI/도메인/reducer/query-runner/캐시 불변(헥사고날 심 교체만). 무-날조·정직 분리·신선도(D061)·읽기전용 준수. 키·토큰은 서버에만(커밋/클라 노출 금지). **런타임은 Node(workerd 차단)** — 클라 `/api/*` 계약은 런타임 무관하게 불변.
