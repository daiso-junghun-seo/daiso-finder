**재개 규칙(새 세션)**: `feat/dev-diagnostics-panel` 플랜은 `main`에 로컬 병합 완료(위 "현재 상태", §B31 참조). 그 위에서 로컬 브랜치 `feat/scan-aim-guide`(`main` 미병합)가 2026-07-28 아이폰 실기기 측정이 드러낸 두 문제 — `경과: 14.1s`의 디코드-시간 오독, 없는 프레임을 겨누라던 조준 문구 — 를 6태스크로 닫았다: `decodeMs` 신설·모서리 브래킷 오버레이·`'계산바코드'` 문구 정정·스캐너 LiveRegion 시각적 숨김·`dev-proxy.mjs`의 `/api/search` 라우팅·§B30-9~11 결정 기록. 이어서 전체-브랜치 최종 리뷰 수정 웨이브(2026-07-28, 위 문단)가 조준 사각형의 프리뷰 초과·`decodeMs`의 구간 분리(`cameraMs`)·주석 사실성·테스트 경화를 닫았다. 이어서 SDD 플랜 `2026-07-30-frame-loop-and-decode-metrics`(4태스크)가 **1단계(계측기 배선)를 완료**했다 — 재시도 루프를 프레임 단위로 하향하고(`frameLoop.ts`), zxing 폴백 디코더를 캔버스 기반으로 재조립하고(`zxingFrameDecoder.ts`), `시도 횟수`·`디코드 점유`·`프레임 복사`·`루프 대기` 4개 카운터를 신설했다(결정 상세 = §B30-14, 게이트 = 위 "현재 상태" 참조). 이어서 **전체-브랜치 최종 리뷰 수정 웨이브(2026-07-30, 위 문단)** 가 계측기의 **해석 규칙 결함 2건**(워밍업이 `루프 대기`에 섞여 잔차 규칙이 발화 불가 / 조립 비용이 `디코드 점유`에 섞여 크롭을 서열화 불가)을 닫고 `워밍업 대기`·`비트맵 조립` 2개 카운터를 더했으며, 이 단계가 만든 **취소 회귀**(두 대기가 abort와 경합하지 않아 카메라가 켜진 채 남을 수 있었다)와 테스트 이빨 3건을 고쳤다(§B30-15). **이 태스크가 배송한 것은 계측기이지 답이 아니다** — 아래 측정 절차는 정정된 판정 규칙을 쓴다.

다음 우선순위는 이 계측기로 하는 **실기기 측정**이다. **비교 기준에 주의**: 조준 가이드(§B30-13) 질문은 `de5b49a`와 동등한 코드(그 위는 문서만 갱신된 커밋들)를 기준선으로 삼을 수 있었지만, **프레임 루프 질문에는 비교 가능한 기준선이 아예 없다** — `decodeAttempts`·`decodeMs`가 "라이브러리 내부 재시도"에서 "앱 소유 루프"로 **의미 자체가 바뀌었기 때문**(§B30-14 ⑥). 그래서 이번 1단계 측정은 옛 수치를 이기는 비교가 아니라 **새 기준선을 세우는 측정**이다.

절차: PowerShell은 `$env:HOST='0.0.0.0'; npm run dev:live`(문서의 `HOST=0.0.0.0 …` 한 줄 표기는 bash 전용이라 PowerShell에서 동작하지 않는다). **폰은 HTTPS가 필수**다 — LAN IP를 http로 열면 `secureContext:false`가 되어 카메라 자체가 열리지 않으므로, 터널(localtunnel 등)은 대안이 아니라 요건이다. 동일 기기·동일 상품·권한 이미 허용 상태로 **최소 2회 측정**하고, 권한 프롬프트가 낀 첫 런과 스캔 도중 백그라운드로 전환된 런은 비교에서 제외한다. 매 런마다 `스캔 소요` · `카메라 승인` · `디코더 준비` · `시도 횟수` · `디코드 점유(조립 포함)` · `비트맵 조립` · `프레임 복사` · `루프 대기` · `워밍업 대기` **9개 값**을 함께 기록한다(마지막 2개는 2026-07-30 최종 리뷰 수정 웨이브 신설 — §B30-15). **패널이 새로 출력하는 캡처빌리티 두 줄**(`지원 제약:` · `카메라 기능:` — `report.ts`의 `captureCapabilitiesLine`, §B30-16)도 함께 받아 적는다: 다음 레버가 `zoom`인지 확인하는 데 쓰인다(2026-07-30에 이미 그 아이폰에서 `zoom=0.5~10`·`torch=true`, `focusMode`는 `지원 제약`에 없음 — 설정 불가로 확인됨, §B30-16 ④).

**최상위 질문(2026-07-30 신설, §B30-16) — 세부 판정 규칙보다 먼저 답한다**: `FRAME_LOOP_MIN_INTERVAL_MS`가 200에서 0으로 배송됐다(§B30-16) — 이번 런은 그 자체가 진단이다.

| 관측 | 함의 |
|---|---|
| 시도 횟수가 22 근처를 유지하고 `스캔 소요`가 **~1.5초로 붕괴**한다(예측 — 아직 관측되지 않았다) | **표본-제한**이었다. 페이싱이 병목이었던 것이고, 이 질문은 닫힌다 |
| 시도 횟수가 **80~100대로 폭증**하는데 `스캔 소요`는 기존 **~4초대에 머문다** | **시간-제한**이다(오토포커스 정착·손떨림·모듈당 픽셀 부족 등 물리적 원인). 표본율을 올려도 소용없다 — 다음 레버는 카메라 `zoom`(확인된 범위 `0.5~10`, §B30-16 ⑤) |
| 시도당 실작업(아래 표의 첫 세 행)이 이전 실측(~42.6/48.8ms)보다 **상승**한다 | 메인스레드 점유 리스크(§B30-16 ③)가 현실화했다는 신호 — 페이싱을 다시 늦추는 것도 함께 검토 대상이 된다. 상승이 없었다고 미리 단언하지 않는다 |

아래 세부 판정 규칙은 이 질문의 답을 세분화한다(**2026-07-30 정정** — 정정 전 규칙 2개는 틀렸다, §B30-15 ①②):

| 값 | 답하는 질문 | 함의 |
|---|---|---|
| **(`디코드 점유` − `비트맵 조립`) / `시도 횟수`** | 시도당 **디코더 자신의** 비용 | 크면 디코더가 느리다 → 2단계(`zxing-wasm`) 정당화. **`디코드 점유` 원값을 그대로 쓰지 않는다** — 조립이 그 안에 들어 있다 |
| `비트맵 조립 / 시도 횟수` | 시도당 캔버스 → 비트맵 비용(`getImageData` 8.3 MB 리드백 + greyscale + binarize) | 크면 원인은 **해상도**다. `zxing-wasm`은 같은 캔버스를 같은 `getImageData`로 읽으므로 **이 값을 줄이지 않는다** → 후보 서열은 **브래킷 크롭 > wasm** |
| `프레임 복사 / 시도 횟수` | 시도당 GPU측 `drawImage` 비용 | 크면 역시 해상도·크롭. wasm 무관 |
| `루프 대기` | 우리가 페이싱으로 버린 시간 | **상수가 0으로 배송된 뒤로는 이 값이 곧 rAF 대기다** — `FRAME_LOOP_MIN_INTERVAL_MS`가 0이라 더 이상 우리가 고른 간격을 곱해 비교할 대상이 없다. 그런데도 이 값이 크면 rAF 자체가 늦게 오는 것(메인 스레드 부하)이며 **워밍업이 아니다** — 워밍업은 자기 필드가 있다 |
| `워밍업 대기` | 비디오가 첫 프레임(치수)을 낼 때까지 우리가 기다린 시간 | 크면 원인은 디코더도, 간격도, 해상도도 아니다 → 루프 시작을 `loadedmetadata`에 걸거나 카메라 기동 비용으로 수용 |
| 잔차 = `스캔 소요` − `카메라 승인` − `디코더 준비` − (`디코드 점유` + `프레임 복사` + `루프 대기` + `워밍업 대기`) | 계상 못 한 시간 | **`비트맵 조립`은 더하지 않는다** — `디코드 점유`의 부분집합이라 더하면 이중 계상되어 잔차가 음수로 간다. 워밍업은 더 이상 잔차의 후보가 아니다(자기 필드로 분리됨), 그래서 잔차가 크다면 그것은 **아직 이름 없는 새 구간**이라는 뜻이다 |

**이전 절차의 "2번째 arm"(간격 상수를 로컬에서만 0으로 낮춰 대조 측정하는 단계)은 제거한다** — 그 arm이 재던 것이 이제 **배송된 기본값 자체**이기 때문이다(§B30-16). 대조 없이 직접 관측하면 되므로 별도 arm은 더 이상 필요 없다.

**성공의 기준은 "빨라졌다"가 아니라 구간들이 분리되어 병목이 표본-제한인지 시간-제한인지 귀속 가능해지는 것**이다 — 느려졌다면 그것대로 기록한다(§B30-16 ③의 메인스레드 리스크가 현실화했을 수 있다는 뜻이다). 이 실기기 측정은 owner가 직접 확인해야 하는 항목이라 새 세션이 대신할 수 없다. 측정 후 **2단계 후보 서열**(① 카메라 `zoom` — 시간-제한으로 나올 경우의 확인된 레버, `focusMode`는 이미 폐기됨(§B30-16 ④) / ② 브래킷 크롭 — 제품 결정 포함, 상자 밖 코드가 안 읽히게 된다 / ③ `zxing-wasm` 이관)과 `main` 로컬 머지 여부를 함께 결정한다.

그 다음 = 🟢 슬라이스 3번(UI 폴리싱 — 후보 리스트 + 사진 스타일) (1번 후보품질 튜닝 ✅ 2026-07-24 `8518337`; 2번 바코드 스캔 ✅ 2026-07-25/26 **`main` 병합 완료**(`9570096`, DataMatrix 정정 `6c33189`)). 스코프 주의 = `.candidate-list`·`.product-photo`(+ 스캔 오버레이 `.scanner-*`)의 **바운드 프레젠테이션 패스, 카피·마크업 시맨틱 불변**. 큰 수(배포·AI 티어링·반대형)는 owner court(ToS·Bible)라 게이트가 풀린 뒤. 병렬 서브에이전트로 최적화하며 진행 가능. 로컬 테스트는 언제든 `npm run dev:live`.

**불변 원칙**: UI/도메인/reducer/query-runner/캐시 불변(헥사고날 심 교체만). 무-날조·정직 분리·신선도(D061)·읽기전용 준수. 키·토큰은 서버에만(커밋/클라 노출 금지). **런타임은 Node(workerd 차단)** — 클라 `/api/*` 계약은 런타임 무관하게 불변.
